# 返修机故障占比估算与校准漂移监测（FastAPI + NumPy）

备件前估算一批返修机中**电源 / 驱动 / 控制**三类故障各有多少台。
上传含「机器编号 + 分类器初判」的 CSV（≤500 台），维修班组随机拆检、
按台登记/更正/撤回实检类别，系统按实检样本拟合未检件的故障占比，
折算台数后加上各类实检数给出全批估计；同时按出厂校准的参考混淆矩阵
累计似然比，**提示哪一类实检故障最先出现偏离出厂校准的证据**。

## 一、估算口径

1. 对已拆检机器，按**实检类别**分组，统计每组中各初判类别的经验概率，
   组成 3×3 混淆概率矩阵 `P`（行=实检，列=初判，每行和为 1）。
2. 未检件的初判经验分布为 `q`（各类未检件初判计数 / 未检台数，和为 1）。
3. 在单纯形约束 `π ≥ 0`、`Σπ = 1` 下，用 NumPy 求使平方误差
   `SSE = ‖Pᵀπ − q‖²` 最小的故障占比 `π`。求解器枚举内部点（等式 KKT）、
   三条边（一维解析解）和三个顶点，取 SSE 最小的可行解，矩阵亏秩时
   仍保证有候选返回（见 `app/estimation.py:_solve_simplex`）。
4. 各类估计台数 = 实检台数 + `π_k × 未检台数`（三类折算之和守恒为未检总数）。

### 门控规则

- **仍有未检件**时，若任一故障类别没有实检样本，或混淆矩阵不满秩
  （`numpy.linalg.matrix_rank` < 3），**撤下估数**并在页面提示补检原因。
- **全部拆完**时不做拟合，直接返回各类实检实数。
- 撤回一台后该台立即重新计入未检，门控与估数随之重算。

### 并发与一致性

- 拆检记录保存在单进程内存中，所有读写经同一把 `asyncio.Lock` 串行化。
  两个浏览器窗口同时登记/更正/撤回（含同一台机器）时，两笔修改都不丢失，
  接口返回的机器明细、实检数、估数与漂移告警始终来自持锁期间的同一份快照。
- 因此部署固定 `uvicorn --workers 1`（见 `docker-compose.yml`）；
  多进程/多副本需换成数据库等共享存储。

## 一点五、漂移监测口径（`app/drift.py`）

维修班组据此判断**哪类实检故障先出现偏离出厂校准的证据**。

1. **参考矩阵录入**：页面可录入 3×3 参考混淆概率矩阵 `R`，行对应实检
   类别、列对应初判类别；每项概率均为正、每行和为 1（行和容差 1e-8）。
   校验在任何状态写入之前完成：无效输入返回 400，**当前矩阵与告警原样
   保留**；有效矩阵立即对本批已有登记记录整体重算。
2. **按登记顺序的累计似然比（LR）**：三个实检类别各维护一条，初值 1。
   每登记一台（实检 `r`、初判 `c`），只更新 `r` 类：

   `LR_r ← LR_r × smooth(r,c) / R[r][c]`

   其中加一平滑**只用该实检类别此前登记的样本**（不含本台）：

   `smooth(r,c) = (1 + 此前 count(r,c)) / (3 + 此前该类样本总数)`
3. **首次过线告警**：记录**首个**使任一类别 LR 达到或超过阈值 **60**
   的机器编号与实检类别；之后即便该比值回落到 60 以下，告警仍保留
   （黏性，只认首次过线点）。
4. **更正 / 撤回 / 再登记**：更正只改实检类别、**保留原位置**；撤回
   **移除**该登记记录、机器回到未检；撤回后再登记作为新记录**排到
   末尾**。每次变更后全部 LR 与首次过线点都按当前记录**重算**：重算后
   没有过线点就撤下告警。
5. **同源快照**：机器清单、估数、LR 与告警在同一把锁内由同一份记录
   生成；系统不缓存历史告警，迟到的旧快照无法恢复已失效的告警。
6. **新批次清空**：重新上传 CSV 会清空登记顺序、参考矩阵与全部监测
   状态，监测从零开始（页面输入框同时重置为默认矩阵，需重新提交）。

接口：`POST /api/drift/reference`，请求体 `{"matrix": [[…3×3…]]}`；
漂移结果随 `GET /api/batch` 及各登记/撤回响应的 `drift` 字段返回
（`reference_matrix`、`likelihood_ratios`、`sample_counts`、`order`、
`alert`）。

## 二、目录结构

```
app/
  estimation.py     # 混淆矩阵、门控、单纯形约束最小二乘（纯 NumPy）
  drift.py          # 参考矩阵校验、加一平滑似然比、首次过线告警（纯 Python）
  csv_utils.py      # CSV 解析与校验（≤500 台、表头/类别别名、重复编号）
  storage.py        # 内存批次存储 + 异步锁 + 登记顺序（更正原位/撤回移除/再登记排尾）
  main.py           # FastAPI 路由（含 /api/drift/reference）
  static/index.html # 单页前端（原生 JS，3 秒轮询同步多窗口改动）
scripts/
  generate_sample.py# 生成演示 CSV（真实占比 45/35/20 + 混淆噪声）
  smoke_check.py    # 对运行中服务的端到端冒烟（含漂移监测全流程、并发两窗口）
tests/              # pytest：求解器交叉验证、门控、漂移核心/API、API 全流程与并发
data/sample_machines.csv  # 120 台示例数据
Dockerfile  docker-compose.yml  requirements.txt
```

## 三、启动方式

### Docker Compose（推荐演示）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

### 本地直接运行

```bash
pip install -r requirements.txt
python scripts/generate_sample.py 120 data/sample_machines.csv   # 可选
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

页面操作：上传 `data/sample_machines.csv` → 在机器行点击
「电源/驱动/控制」登记或更正 → 「撤回」使该台重算未检；
上方卡片实时显示实检数、未检折算、全批估计、`P`/`q`/`π` 与 SSE，
以及补检提示。

### 漂移监测演示（更正如何改变告警）

1. 上传一个小批次（如 5 台初判均为「控制」的机器），在「3. 漂移监测」
   卡片确认参考矩阵（已预填默认出厂矩阵，可直接点「录入/更换参考矩阵
   并重算」；每项须为正、每行和为 1，否则被拒绝且现状不变）。
2. 依次把前 3 台登记为实检「电源」：电源类 LR 约为 4.76 → 34.01 →
   **291.55**，第 3 台首次达到阈值 60，页面红色告警锁定该机器编号与
   实检类别；登记顺序表中该行标 🚩。
3. 继续登记两台「初判电源、实检电源」的机器，当前电源 LR 会回落到 60
   以下，但**告警仍保留**（黏性）。
4. 把第 3 台**更正**为实检「控制」（原位置不变）：电源类重算后无过线
   点，红色告警撤下；再把它**撤回**后重新登记为「电源」，记录排到末尾
   并在末尾重新过线、告警重新出现。

### CSV 格式

表头支持 `机器编号,初判` 或 `id,initial`（UTF-8，含 BOM 亦可）；
类别支持中英文：`电源/power`、`驱动/drive`、`控制/control`。
编号不可重复，空行容忍，超过 500 台或类别非法返回 400 及中文原因。

## 五、已验证结果

- `pytest`：**35 项全部通过**（原 19 项 + 漂移相关 16 项）。求解器与细网格
  暴力参考解在 12 组随机矩阵上交叉验证（SSE 不劣于参考解），并覆盖精确
  还原、边界（零分量）解、缺类/不满秩门控、全检实数等场景；漂移测试覆盖
  参考矩阵三类非法输入拒绝、加一平滑「仅用本类此前样本」的手工核对、
  首次过线位置、回落黏性、更正原位重算撤警、撤回移除/再登记排尾、换矩阵
  重算、新批次清空与快照同源；API 测试覆盖上传校验、登记、更正、撤回、
  400/404 错误路径及 `asyncio.gather` 并发。
- 真实 uvicorn 服务端到端冒烟 **全部 PASS**：估测主流程（上传 120 台 →
  满秩估数恢复且台数守恒 → 更正/撤回/门控/补检 → 并发两笔均生效 →
  全检实数 39/59/22）保持原行为；漂移流程覆盖新批次清空 → 三类无效矩阵
  400 且不改变状态 → 有效矩阵录入 → 第 3 台锁定首次过线（LR=291.55）→
  低比值登记使 LR 回落至 21.69 但告警保留 → 更正后重算无过线点撤警 →
  撤回移除/再登记排尾并重新过线 → 再传批次监测彻底清空。
- 前端：页面脚本通过 Node 语法解析；HTTP 复演了网页演示序列（上传→录入
  矩阵→登记出警→更正撤警→撤回再登记重新出警→无效矩阵被拒不影响现有
  告警）。页面 3 秒轮询只刷新数据展示，不覆盖用户尚未提交的矩阵编辑。
- 边界：501 台拒绝、500 台接受；非法类别/未知机器/空上传均返回 400；
  参考矩阵含零/负值、行和≠1、非 3×3、非数值/布尔均返回 400；极端连乘
  （2000 台）产生 `inf` 时阈值判断与告警仍安全有效。

## 六、未完成项 / 已知限制

1. **本环境未安装 Docker**，`docker compose up --build` 未在本机实际执行；
   Dockerfile/compose 未改动，仅做了 YAML 语法与配置核对，需在有 Docker
   的环境再跑一次确认（容器内 `requirements.txt` 的固定版本可正常解析，
   本机因包索引缺少 `pytest-asyncio==1.1.2`，自测改用 1.1.1，不影响应用
   代码与镜像构建）。
2. 内存存储 + 单 worker：服务重启或重新上传会清空拆检记录与漂移监测；
   没有用户/多批次隔离，同一时刻只保留一个批次。
3. 估测的经验混淆矩阵直接采用样本频率，未做平滑；某类实检样本很少时
   概率估计噪声较大（门控只保证三类齐且满秩，不保证样本量充足）。漂移
   监测的预测概率则按需求采用加一平滑，两者口径不同。
4. 似然比在极长序列下可能溢出为 `inf`（浮点行为，阈值判断不受影响）；
   未做对数空间累加，页面以指数形式显示大数值。
5. 估数台数为折算小数（页面保留两位小数），未做取整分配；如需整数备件
   建议，可另加最大余数法取整。
6. 前端轮询间隔固定 3 秒，未用 WebSocket 推送。
